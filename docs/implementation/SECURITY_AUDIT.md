## 2. Карта путей выполнения команды
| Вход (дверь `origin::Source`) | Куда приходит | Что проверяется перед действием |
|---|---|---|
| Голос (`voice`), консоль, окно (`window`), локальный IPC (`ipc`) | `app.rs::execute_command` | лицензия (`access::check`), пароль владельца для `high`, подтверждение «да» с того же входа (`confirm::gate`), далее `policy::authorize` на каждой операции |
| Телефон (`phone`) `/cmd` | `remote.rs` → `remote::submit(Phone)` → тот же `execute_command` | то же + секрет устройства, **теперь** время и уникальный номер запроса (`replay.rs`), журнал |
| Телефон: разделы `/api/*`, `/act` | `ui::phone_get` / `ui::phone_act` (дверь `phone`) | список разрешённого, журнал, `policy::authorize` для запуска программ/игр |
| Telegram (`telegram`) | `remote::submit(Telegram)` → `execute_command` | сопряжённый чат, далее как выше |
| Планировщик | `scheduler::start` → `remote::submit(<дверь задания>)` | **теперь** задание хранит дверь, с которой создано |
| Сценарии (шаги) | `scenario::run_step` под `enter_command("scenario","medium")` | `policy::authorize`: опасное (`high`) отказано всегда |
| Автопилот | план ИИ → движок сценариев | разрешение «Автоматизация» (выключено по умолчанию), показ плана и «да», затем как сценарий |
| Lua-команды | API `jarvis.*` | `policy::authorize*` в `system.rs` (запуск, открытие, ввод, мышь, буфер, окно) и `fs.rs` (файлы); `jarvis.http` — **теперь** с запретом loopback/LAN |
| Новые функции (память, мессенджер, умный дом, перевод…) | `features::handle` (один вызов в `execute_command`) | `perms::check`, `owner::guard`, подтверждение; **теперь** запись в журнал для удалённых дверей |
| Кнопки окна | `ui::run_action` | подписанный секрет окна, список действий под `owner::guard` |

Вывод по картине: единая точка исполнения операций уже существовала (`policy::authorize`); реальные пробелы были в трёх местах (см. F-03, F-04, F-12) и в доставке запросов с телефона (F-02).

## 4. Модель доступа (что на каком уровне риска)
- **low** — чтение и безобидные действия (время, погода, громкость). Любая дверь, без подтверждения.
- **medium** — открытие программ и ссылок, ввод, файлы пользователя. Любая дверь; удалённые двери пишутся в журнал. Внутри сценария потолок — medium.
- **high** — выключение, удаление, запуск скриптов и неизвестных программ. Только внутри команды с подтверждением «да» **с той же двери**; при заданном пароле владельца — только при разблокированной программе; **без** запущенной команды (кнопка, шаг, задание, шлюз телефона) удалённая дверь не может выполнить такую операцию вообще.
- Пароль владельца: защищает действия, которые меняют то, что Jarvis хранит или может (сообщения, память, контакты, расписание, разрешения, установка, умный дом, привязка устройств, очистка журнала). Голосом разблокировать нельзя; с телефона разблокировать, сменить или снять пароль нельзя.

## 5. Секреты и подпись Android
- Поиск по отслеживаемым файлам и по всей истории git: приватных ключей (`BEGIN … PRIVATE KEY`), ключей AWS/GitHub/Slack/Google/OpenAI в коде нет. Единственные «ключи» — тестовые заглушки в тестах (`sk-abcdefghijklmnop12345`, поддельный токен Telegram).
- Единственный реальный закрытый ключ в Git — `android/keystore/jarvis-sideload.jks`, добавлен коммитом `7b8121c`. Пароль хранения и ключа (`jarvis-sideload`) был открытым текстом в `android/app/build.gradle` и `android/README.md`.
- Репозиторий публичный → ключ считается **раскрытым**. Им подписаны артефакты сборок Android #1 и #2.
- Ключ подписи Windows и лицензионный сервер: берутся из секретов CI (`WINDOWS_CERT_PFX_BASE64`, `WINDOWS_CERT_PASSWORD`) и файлов на сервере (`JARVIS_LS_SIGNING_KEY_FILE`); в репозитории их нет. CI уже проверяет, что приватные ключи не попали в пакет клиента.
- DPAPI: секреты (ключи ИИ, токены) хранятся через DPAPI Windows (шифрование под учётной записью пользователя), не кодированием. Это защищает от копирования файла на другой компьютер/пользователя, но **не** от программы, запущенной тем же пользователем. Проверено чтением кода; на живом Windows не проверялось.
