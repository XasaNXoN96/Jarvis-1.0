## F-02 Повтор запросов телефона — `crates/jarvis-core/src/replay.rs` (новый), `remote.rs`, `remote_page.html`
- Каждый `POST`, меняющий состояние (`/cmd`, `/act`, `/voice`, `/voiceprint-do`, `/voice-audio`), несёт время телефона `X-Ts` и уникальный номер `X-Rid` (8–64 знака `A-Za-z0-9_-`).
- Компьютер принимает запрос, если время отличается от его часов не более чем на 120 с и номер не встречался. Принятые номера пишутся в файл `remote_nonces.json` и переживают перезапуск; хранятся 300 с (дольше запрос всё равно не может быть действителен).
- Повторная доставка: ответ `200 {"duplicate":true}`, действие **не** выполняется (идемпотентность). Устаревший или «из будущего» запрос — `409` с временем компьютера; нет времени/номера или они испорчены — `400`.
- Лимит: 30 новых запросов за 10 секунд на устройство (`429`).
- Страница и приложение узнают разницу часов из ответа `/poll` (`now`) и при `409` повторяют запрос один раз с НОВЫМ номером, поэтому неверные часы телефона не ломают работу.
- Чего это не делает: см. F-11 (кража секрета при http).

## F-01 Ключ подписи Android — план ротации (ВЫПОЛНЕН: см. раздел «F-01 — ЗАКРЫТО» ниже)
Сделано в коде: `android/app/build.gradle` больше не содержит пароля по умолчанию; ключ берётся из окружения (`JARVIS_KEYSTORE`, `JARVIS_KEYSTORE_PASSWORD`, `JARVIS_KEY_ALIAS`); старый ключ используется только при `JARVIS_ALLOW_LEGACY_KEY=1`, и такой пакет в CI называется `…-LEGACY-KEY.apk`. Workflow `build-android.yml` берёт ключ из секретов репозитория `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` и печатает предупреждение, если их нет. Файл старого ключа **не удалён** (чтобы не сломать сборку и обновления без вашего решения). Workflow `security-audit.yml` напоминает о нём при каждом запуске.

Что сделать вам:
1. На своём компьютере создайте новый ключ (пароль придумайте длинный и нигде не публикуйте):
   `keytool -genkeypair -keystore jarvis-release.jks -alias jarvis -keyalg RSA -keysize 4096 -validity 36500`
2. Закодируйте файл: `base64 -w0 jarvis-release.jks` (Windows PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("jarvis-release.jks"))`).
3. GitHub → Settings → Secrets and variables → Actions → добавьте три секрета: `ANDROID_KEYSTORE_BASE64` (результат шага 2), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` (`jarvis`). Сам файл `.jks` в репозиторий не кладите; храните копию в менеджере паролей.
4. Запустите сборку Android; артефакт будет без суффикса `-LEGACY-KEY`.
5. **Миграция на телефоне:** подпись изменится, поэтому Android не поставит новую версию поверх старой. Удалите приложение Jarvis (данные приложения — только адрес компьютера) и установите новое; привяжите телефон заново (код привязки). Настройки на компьютере не теряются.
6. Когда новая версия установлена и работает, удалите `android/keystore/jarvis-sideload.jks` из репозитория и ветку `JARVIS_ALLOW_LEGACY_KEY` из workflow. Выпущенные ранее APK со старым ключом считайте недоверенными и удалите.
7. Историю Git переписывать не нужно и не поможет: репозиторий публичный, ключ уже скомпрометирован навсегда — важна только замена.

### Ключ Android: самый короткий путь для владельца (проверено 22.10.2026)
Одно действие на вашем компьютере (нужны JDK и GitHub CLI `gh`; в скрипте для Windows ключ ищется в PATH, JAVA_HOME, Android Studio и Temurin):
1. `gh auth login --web` (один раз, откроется браузер) — это единственный шаг, который нельзя сделать за вас: нужны ваши учётные данные GitHub.
2. `bash tools/android-key/make-key.sh` (Windows: `powershell -ExecutionPolicy Bypass -File tools\android-key\make-key.ps1`). Скрипт создаёт новый ключ, задаёт три секрета и печатает только имена секретов и открытый отпечаток сертификата. Если `gh` не вошёл, ключ сохраняется, а после `gh auth login` достаточно запустить скрипт с `--upload` (Windows: `-Upload`).
3. Сказать «ключ создан»: проверку выполнит workflow «Android key status» (Actions → Run workflow, либо я запущу сам): он без сборки и без вывода секретов проверяет, что секреты заданы, ключ открывается паролем и его отпечаток **отличается** от старого скомпрометированного.
Проверено автоматически: скрипт `.sh` выполнен в изолированной среде с настоящим `keytool` и имитацией `gh` (два запуска → разные пароли и ключи; пароль не попал в вывод; права 700/600; повторный запуск не заменяет ключ; `--upload` работает; ключ открывается паролем, PKCS12, алиас `jarvis`); пароль передаётся через переменную окружения, а не в командной строке. Скрипт `.ps1` **не запускался** (PowerShell в среде разработки нет) — проверен чтением; значения в `gh secret set` подаются из файлов через `cmd /c "... < файл"`, потому что конвейер PowerShell добавляет к значению перевод строки (CI дополнительно убирает `\r\n` из пароля и алиаса).
Что не автоматизируется: запись секретов в репозиторий требует прав владельца (токен среды разработки недействителен для этого, права записи секретов у CI нет), а создание ключа внутри публичного CI небезопасно (ключ некуда положить, кроме журналов и общедоступных артефактов).
Состояние на 22.10.2026: секреты **не заданы** (workflow «Android key status» #1 красный: `MISSING` ×3, без вывода секретов); debug-APK собирается без релизного ключа (Android #5, #7, #8, #9 зелёные); release без секретов падает с понятной ошибкой (Android #6).
