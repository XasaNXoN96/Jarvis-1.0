## 2. Где и почему Android принимает сертификат без проверки
1. `Address.normalize`: адрес без схемы превращается в `http://…` — по умолчанию шифрования нет.
2. `network_security.xml` и манифест разрешают открытый http для любого адреса.
3. `MainActivity.onReceivedSslError`: для введённого адреса вызывается `proceed()` **при любой ошибке сертификата**. Причина — сертификат самоподписанный и выпущен на IP; обычная проверка всегда даёт ошибку. Сейчас проверяется только имя хоста, а не сам сертификат, поэтому любой узел в сети, подменивший адрес ПК (ARP-подмена, поддельная точка доступа), принимается.
4. Дополнительно: QR несёт общий секрет по открытому http, код привязки идёт тем же каналом.
Серверная часть (rustls) работает корректно; уязвимость — в клиенте и в способе выдачи ссылки.

## 3. Предлагаемая архитектура
### 3.1 Принцип
Доверие строится на **закреплённом открытом ключе ПК** (SPKI SHA-256), полученном вне канала (экран ПК), а не на центрах сертификации и не на имени/IP. Ключ ПК долговечен и не зависит от IP. Сертификат — «обёртка» с актуальным списком адресов, которую ПК перевыпускает тем же ключом.

### 3.2 Сторона ПК
- **Постоянная пара ключей** `remote_key` (создаётся один раз, хранится на диске в запечатанном виде DPAPI через `secret.rs`; ошибка записи — явная ошибка, а не молчание).
- **Сертификат перевыпускается тем же ключом** при смене набора адресов и за 30 дней до окончания (`rcgen::CertificateParams::self_signed(&key)`), срок 2 года. IP меняется → отпечаток **не** меняется.
- **Отпечаток** `sha256/<base64url(SHA-256(SPKI DER))>` + короткая форма для глаз (пары по 4 hex-символа).
- **Окно Jarvis → Пульт:** показывает код привязки, отпечаток, QR для привязки, список устройств, кнопки «Отозвать», «Сменить ключ ПК» (за паролем владельца, с предупреждением «все телефоны придётся привязать заново»).
- **Обычный http:** принимается **только с 127.0.0.1** (туннель `cloudflared`). С локальной сети — ответ-перенаправление на https без чтения секретов; переключатель «Разрешить http в домашней сети (небезопасно)» выключен по умолчанию, при включении в окне постоянная красная плашка, событие в журнале безопасности.
- **QR привязки**: `https://ip:9713/#pin=sha256/…&c=<код>` (фрагмент не уходит по сети). Общий секрет `?t=` в QR для локальной сети больше не кладётся (для туннеля остаётся, это уже https).

### 3.3 Сторона Android
- **`Pin.java`** (чистая Java): разбор отпечатка, сравнение за постоянное время, решение `PinPolicy.decide(ошибки, SPKI, закреплённый отпечаток, время)`.
- Принятие сертификата в `onReceivedSslError`: сертификат приводится к X509 (API 29+ `getX509Certificate`; API 26–28 — разбор `SslCertificate.saveState`), считается SPKI-хэш.
  - хэш = закреплённому **и** ошибки ⊆ {UNTRUSTED, IDMISMATCH} → `proceed()`;
  - иначе `cancel()` и понятный экран: «Не тот компьютер / сертификат изменился», «Срок сертификата истёк» (ПК перевыпустит сам), «Дата на телефоне неверна» (NOTYETVALID), без кнопки «всё равно открыть».
- **Первая привязка без тихого «доверия при первом знакомстве»:**
  - через QR/ссылку: отпечаток приходит из QR и сверяется при первом рукопожатии;
  - вручную (IP + код): приложение загружает публичную страницу `GET /` (секретов не отправляет), показывает диалог «Отпечаток ПК: A1B2-C3D4-…; сверьте с окном Jarvis» и **только после подтверждения** сохраняет отпечаток; **код привязки отправляется лишь после этого**, иначе подменивший сервер получил бы код и перепослал его настоящему ПК.
- Схема по умолчанию `https://`; `Address.normalize` отвергает `http://`; манифест: `usesCleartextTraffic=false`, `network_security.xml`: `cleartextTrafficPermitted=false`. Скрытого возврата на http нет.
- Личный секрет устройства хранится в приложении (мост `JarvisAndroid`, закрытое хранилище приложения) и подставляется страницей, поэтому смена IP не требует новой привязки (иначе секрет потерялся бы вместе с `localStorage` старого источника).

### 3.4 Смена IP, смена сертификата, повторная привязка, отзыв
| Событие | Что происходит | Нужно ли действие |
|---|---|---|
| Новый IP ПК (DHCP, другая сеть, VPN) | ключ тот же → отпечаток тот же; ПК перевыпускает сертификат; телефон принимает (ошибка IDMISMATCH допустима при совпадении ключа) | телефон: «Изменить адрес ПК» (отпечаток и секрет сохраняются) |
| Продление сертификата | тот же ключ, новый срок | нет |
| Истёк сертификат (не продлился) | телефон отказывает; ПК при запуске/смене адреса продлевает автоматически; диагностика ПК предупреждает за 30 дней | перезапуск Jarvis |
| Подмена сервера | другой ключ → отпечаток не совпадает → блокировка с понятным текстом | владелец проверяет сеть; при необходимости привязывает заново |
| Смена ключа ПК (явная или потеря `remote_key`) | отпечаток другой → телефон блокируется (никакого автоприёма) | «Привязать заново»: новый код + сверка нового отпечатка; старое закрепление заменяется только после подтверждения |
| Отзыв устройства | запись отозвана → 403; страница возвращается к экрану привязки; другие устройства не затронуты | нет |
Опционально позже: «следующий ключ» (два закреплённых отпечатка) для плановой ротации без перепривязки.

## 4. Как не заблокировать владельца
- Окно Jarvis на ПК работает через loopback и свой токен — **от пульта не зависит**; владелец не может потерять доступ к ПК, только к телефону.
- Отпечаток привязан к ключу, а не к IP: типичная смена адреса не ломает привязку.
- Секрет устройства хранится нативно: переживает смену источника.
- Блокировка телефона всегда лечится на ПК: новый код (5 минут), «Отозвать», «Сменить ключ ПК»; инструкция показывается в самом экране ошибки телефона.
- Автопродление сертификата с запасом 30 дней и предупреждение в диагностике; ошибки записи ключа/сертификата больше не проглатываются.
- Запасной путь без локальной сети: туннель Cloudflare (настоящий сертификат, независим от IP).
- Резервная копия: ключ `remote_key` в папке данных; при полной очистке папки — перепривязка (это документируется).

## 5. Совместимость с существующим
- **Команды, `/act`, `/api/*`, шлюз телефона:** маршруты и заголовки не меняются; идут внутри TLS.
- **Anti-replay (`replay.rs`):** остаётся как вторая линия (защита от записанного запроса); TLS добавляет конфиденциальность и защиту от подмены. Лимиты, троттлинг, правило дверей, пароль владельца не ослабляются.
- **Туннель:** `cloudflared` по-прежнему ходит на `http://127.0.0.1:9713` — loopback-http остаётся разрешённым.
- **Интерфейс:** карточка «Пульт» получает отпечаток, QR привязки, переключатель http, кнопку «Сменить ключ»; страница пульта — экран привязки с подтверждением отпечатка; сообщения об ошибках сертификата.
- **Браузер телефона (не приложение):** по-прежнему предупреждение о сертификате и нет закрепления; для браузера рекомендация — VPN/туннель. Это остаётся ограничением.

## 6. Тесты
**Rust (`remote.rs`, новый `remote_tls.rs`):** ключ стабилен между перезапусками; смена набора IP → тот же SPKI и новый сертификат с нужными SAN; продление при <30 днях; отказ записи ключа — явная ошибка; http с не-loopback адреса не читает секрет и редиректит, loopback работает; сервер с «разрешить http» пишет событие в журнал; QR привязки не содержит общего секрета; существующие тесты replay/pairing/remote остаются зелёными.
**Java (JUnit, без телефона):** `PinPolicy.decide` для всех случаев: корректный сертификат (совпал отпечаток, срок действителен) → принять; **недоверенный** (нет закрепления) → «спросить»; **подмена сервера** (другой ключ при том же адресе/имени) → отказ; **истёкший** → отказ с подсказкой; **ещё не действителен** (часы телефона) → отказ с подсказкой; **смена сертификата при том же ключе** → принять; **смена ключа** → отказ; **повторная привязка** — закрепление заменяется только после подтверждения; `Address.normalize` отвергает http; сравнение отпечатков за постоянное время. Встроенный `HttpsServer` на тестовых сертификатах проверяет логику на настоящем рукопожатии.
**Chromium:** страница привязки: код не отправляется до подтверждения; сообщения при 403/429.
**Вручную (телефон + ПК):** привязка по QR и вручную; смена IP; подмена (второй ПК/точка доступа); истечение (сдвиг даты ПК); отзыв; повторная привязка; туннель.

## 9. Риски
- **WebView:** нужно подтвердить на устройстве, что `onReceivedSslError` вызывается и для `fetch`/XHR и как долго запоминается решение; запасной вариант — перехват через `shouldInterceptRequest` (дороже).
- API 26–28: разбор сертификата без `getX509Certificate`.
- Часы ПК/телефона (истёкший/ещё не действителен) — понятные сообщения и автопродление.
- Потеря или смена `remote_key` → перепривязка всех телефонов.
- Приложение без сторонних библиотек: сканер QR внутри приложения потребует камеры и библиотеки — **решение владельца**; базовый вариант: ручной ввод + сверка отпечатка, QR открывается как ссылка `jarvis-pair://`.
- Браузерный доступ по сети остаётся без закрепления.

## 10. Критерии приёмки
1. Подмена сервера (другой ключ при том же адресе) отвергается приложением без кнопки «всё равно»; тест + ручная проверка.
2. Смена IP не требует перепривязки; смена ключа — требует, с явным подтверждением нового отпечатка.
3. Код привязки не отправляется до подтверждения отпечатка; общий секрет не передаётся по открытому каналу.
4. С локальной сети http не принимает секреты; loopback-туннель работает; переключатель выключен по умолчанию и виден.
5. Существующие тесты replay/pairing/remote/policy зелёные; новые тесты Rust и JUnit зелёные; Windows и Android CI зелёные для актуального коммита.
6. Ручная проверка на реальных ПК и телефоне выполнена владельцем.

## 11. Влияние на существующие установки
- **Android:** смена ключа подписи уже требует удалить старое приложение; новое приложение работает только по https и закрепляет ПК, поэтому все телефоны привязываются заново (один раз). Старые записи устройств на ПК остаются до отзыва или 90 дней простоя — их стоит отозвать.
- **ПК:** при первом запуске создаётся постоянный ключ (отпечаток новый), сертификат перевыпускается; браузеры снова покажут предупреждение один раз. Ссылки с `?t=` по http с локальной сети перестают работать, пока не включён переключатель; ссылка туннеля работает как раньше.
- **Данные:** память, настройки, лицензии не затрагиваются.
