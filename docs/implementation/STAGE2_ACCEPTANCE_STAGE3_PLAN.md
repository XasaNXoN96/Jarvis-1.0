- `build-android.yml` берёт ключ из секретов `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`. Если их нет, молча собирает старым ключом с суффиксом `-LEGACY-KEY`. **Последняя сборка Android #4 имеет артефакт `Jarvis-Android-22.10.2026_17-30_bdc1fe2-LEGACY-KEY`: CI продолжает использовать старый ключ, секреты не заданы.**

**Что делает владелец (на своём компьютере, пароль нигде не публикуется и не вставляется в чат):**
1. Создать ключ: `keytool -genkeypair -v -storetype PKCS12 -keystore jarvis-release.jks -alias jarvis -keyalg RSA -keysize 4096 -validity 36500` (длинный случайный пароль из менеджера паролей; один пароль для хранилища и ключа).
2. Сохранить копию `jarvis-release.jks` и пароль в менеджере паролей/офлайн-копии. Потеря ключа = невозможность обновлять приложение.
3. Закодировать: Linux/macOS `base64 -w0 jarvis-release.jks`; Windows PowerShell `[Convert]::ToBase64String([IO.File]::ReadAllBytes("jarvis-release.jks"))`.
4. GitHub → Settings → Secrets and variables → Actions → New repository secret: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` (= `jarvis`). Файл `.jks` в репозиторий не добавлять.
5. Запустить «Build Android app»; в имени артефакта не должно быть `-LEGACY-KEY`. Проверка подписи: `apksigner verify --print-certs` — отпечаток должен отличаться от старого.
6. Установить новый APK: Android не обновит приложение поверх старого с другой подписью. Удалить старое приложение (в нём хранится только адрес компьютера), поставить новое, привязать телефон кодом заново. Старые APK считать недоверенными и удалить.
7. После успешной установки (отдельное согласование): удалить `android/keystore/jarvis-sideload.jks`, ветку `legacy` в `build.gradle` и `JARVIS_ALLOW_LEGACY_KEY` в workflow.

**История Git:** переписывать не нужно и не поможет — репозиторий публичный, ключ уже скопирован. Важна только замена ключа. Автоматически историю не трогаю; переписывание (`filter-repo`) возможно только по отдельному разрешению и не снимает компрометацию.

**Предложение (не внедрено, нужно согласие):** после установки секретов заменить молчаливый откат на старый ключ ошибкой сборки, чтобы подписанный публичным ключом APK не мог появиться случайно.

### B. Связь телефона с ПК (F-11)
**Как сейчас (проверено):**
- Один порт 9713 отвечает и по http, и по https (самоподписанный сертификат ПК, `remote.rs::serve`, `tls_current`).
- Авторизация: секрет ссылки или личный секрет устройства (хранится хэш); изменяющие запросы несут время `X-Ts` и уникальный `X-Rid` (`replay.rs`: ±120 с, номера в файле, 429-лимит); для опасных команд правило дверей. Это защищает от **повтора записанного** запроса, но не от **подслушивания**: по http секрет читается в сети и затем используется для новых запросов с правильными заголовками.
- Android: адрес без схемы превращается в `http://` (`Address.java`), `cleartextTrafficPermitted=true`. При https приложение принимает **любую** ошибку сертификата для введённого адреса (`MainActivity.onReceivedSslError` → `proceed()`), то есть шифрование есть, но активного подмена (MITM) в локальной сети оно не остановит: отпечаток сертификата не закреплён.
- Микрофон страницы телефона уже требует https.

**Варианты (нужен выбор владельца):**
| Вариант | Что меняется | Плюсы | Минусы / риски |
|---|---|---|---|
| **O1. https по умолчанию + закрепление отпечатка (рекомендую)** | Android: схема по умолчанию `https://`; отпечаток SHA-256 сертификата ПК передаётся при привязке (в окне ПК и ссылке/QR) и сохраняется; `onReceivedSslError` сравнивает отпечаток вместо `proceed()`; http — только явным переключателем «разрешить http». Windows: показать отпечаток, порт тот же | закрывает подслушивание и MITM без внешнего сервиса; без миграции ПК | нужна работа на двух сторонах; сертификат ПК меняется при смене адреса → перепривязка; на API 26–28 разбор сертификата через `SslCertificate.saveState` (API 29+ — `getX509Certificate`); два пути (http/https) на переходный период |
| O2. VPN (Tailscale/WireGuard) | без изменений кода: адрес из VPN, внутри VPN http допустим | самый простой по коду, работает вне дома | нужен VPN на обоих устройствах; безопасность = безопасность VPN; не решает http в домашней сети без VPN |
| O3. Туннель Cloudflare (уже есть) | ничего | https без настройки | трафик идёт через сторонний сервис; секрет в адресе; новый адрес при каждом включении |

Любой вариант не заменяет существующую авторизацию и защиту от повторов, а дополняет её. Пока выбор не сделан, рекомендация владельцу: использовать https-ссылку и/или VPN, http — только в доверенной сети.
